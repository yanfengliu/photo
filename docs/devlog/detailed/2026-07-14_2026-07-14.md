## 2026-07-14 09:40 — GPU preview uses one sRGB transfer (v0.2.10)

**Action.** Closed a verified prerequisite parity defect before tuning slider envelopes. `viewer.rs` creates the photo and blur textures as `Rgba8UnormSrgb`, so wgpu samples already arrive in linear RGB; iced also selects an sRGB presentation target when the adapter offers one. `image.wgsl` nevertheless decoded every photo/blur sample and encoded its output again. The shader now consumes the hardware-decoded samples directly. It writes linear values to an sRGB target and uses a uniform-controlled manual final encode only for iced's documented non-sRGB surface fallback. All five image/blur texture sites share one format constant, and the longstanding numeric viewer/crop/checker gray values remain unchanged and are consistently treated as linear under the corrected output contract.

**TDD and result.** The red regression inspected the live shader contract and failed on its manual source decoder. The green test pins the shared sRGB texture format, rejects any shader-side source decoder, covers sRGB and non-sRGB output-target selection, checks the extended Rust/WGSL uniform layout, and anchors byte 128 at Exposure +1 to byte 176. Both fresh pre-fix sessions reproduced the same lens-off Exposure +1 mismatch on `test_photos/test.jpg`. Final release-harness run `20260714-163056Z-35340` reports Exposure 1 with every other slider neutral, captures the real GPU frame, and produces a matched 1380×920 CPU render. The measured GPU photo rectangle is physical x=0..1379 and y=152..1071 in the 1800×1200 screenshot; the manually derived `gpu-photo-crop.png` and `before-after-absdiff.png` are local analysis artifacts rather than harness-manifest commands. The GPU/CPU luma means are 199.54/199.12 with p50 205/205; RGB means differ by at most 0.72 and mean saturation by 0.00023. The 0.00759 highlight-clipping gap is consistent with the GPU using bilinear texture minification while the CPU artifact uses Triangle resizing; the former double-digit tone bias is gone. The pre/post CPU artifacts are byte-identical, while the real screenshots differ across 58.05% of pixels (mean absolute RGB 7.53/12.03/7.72). The session finalized via `quit` and left no owned process.

**Reviewer comments.** The first independent refuter confirmed the double transfer against the live shader and resolved iced/wgpu sources, then found three MEDIUM contract gaps: the initial patch assumed every target was sRGB, the CPU-only numeric anchor did not prove the runtime path, and converted checker/crop literals would have changed longstanding UI grays. The target-format uniform and non-sRGB branch close the fallback; the real GPU harness remains required proof; git history confirms the numeric checker values are longstanding, so the patch preserves them and now gives them one consistent linear interpretation. The reviewer also identified pre-existing lens-enabled interpolation-domain drift: GPU texture filtering is linear while the CPU lens sampler interpolates encoded bytes. This pass and its evidence are explicitly lens-off; the lens path remains a separate follow-up rather than an overclaimed parity result. Final independent re-review is synthesized in `docs/threads/current/natural-edit-ranges/2026-07-14/2/REVIEW.md`.

**Reasoning.** Identity edits concealed the transfer bug because the duplicate decode and encode largely canceled each other. Any non-neutral operation between them did not cancel, so range tuning against the dark GPU preview would have compensated for a presentation defect and made exported files wrong. Establishing one-transfer parity first makes subsequent naturalness judgments meaningful.
