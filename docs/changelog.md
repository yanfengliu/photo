# Changelog

External-facing changes per version. Newest first. Dev-internal detail lives in `docs/devlog/`.

## 0.2.9 — 2026-07-14

RAW images and embedded RAW previews are no longer enlarged just because the GPU can accept a larger texture. The shared RAW conversion helper previously called image 0.25's `thumbnail(16384, 16384)` unconditionally; unlike Photo's raster-thumbnail helper, that API scales up as well as down. A 9504×6336 Sony RAW therefore became a 16384×10923 buffer—roughly 179 million pixels—before display, caching, editing, and harness measurement. Conversion is now downscale-only: source-sized images remain source-sized, while an image exceeding the requested bound still scales down exactly as before. Persisted decoded RAW cache entries re-derive once under contract version 7 so accidental upscales are not reused; user-authored baked local edits are preserved. The self-play harness proves the affected fixture now stays 9504×6336 against its 9728×6656 logical sensor dimensions, down from the prior 16384×10923 buffer. Validation includes exact no-upscale pixel coverage, exact normal/rotated embedded-preview and full-develop dimensions, the full decode test group, an independent adversarial re-review, and the four Rust gates.

## 0.2.8 — 2026-07-07

Agent harness release: the app can now be driven end-to-end by an AI agent, the way a user drives it. Launching with `photo.exe --harness[=PORT]` starts a localhost JSON-lines control channel (token-gated, port 7878 by default) plus a per-run artifact directory under `tmp/harness-runs/<run-id>/` containing a connection file, an append-only request/response log that doubles as a replayable script, a run manifest (app version, start/end, stop reason, artifact list), and every captured artifact. The bundled `harnessctl` client sends single commands or replays JSONL scripts. The command vocabulary is deliberately player-level and routes through the exact code paths real input takes: `open`/`import_files`/`import_folder`, `set_slider` (real drag semantics: two change events + release, range-clamped, safe against the double-click-reset affordance), `click` (named buttons/toggles/selects), `key` (the real keyboard dispatch), `set_crop` (requires crop mode, commits like a drag), and `wait_idle` — the synchronization point that covers staged loads, EXIF reads, edit persists, and saves. Observation is dual-channel by design: `screenshot` captures the true GPU frame (what the user sees, UI chrome included), while `dump_render` writes the CPU render — pixel-identical math to the export path — with statistics computed at full resolution: per-channel and luma percentiles, clipping fractions, a 64-bin luma histogram, and mean saturation; `image_stats` and `compare_images` measure any PNG/JPEG pair (mean/max per-channel deltas, differing-pixel fraction). `observe` reports the whole UI state plus a typed controls list generated from the same range/step sources the panel renders from. Harness sessions sandbox all storage (`library.txt`, `collections.json`, `decoded-cache/`, `local-edits/`, `edited/`) into the run directory so they can never pollute the real library; `--harness-real-storage` opts out. Normal (non-harness) launches are byte-identical to 0.2.7 in behavior. Also in this release: the save pipeline's in-flight state is now tracked (found by the first live harness run: `wait_idle` previously reported idle while an export was still being written), and the security-audit pass that the harness's dependency change mandated upgraded quick-xml 0.37→0.41 (two high-severity DoS advisories; the Lensfun XML parser was migrated to the new entity-reference event model) and crossbeam-epoch past RUSTSEC-2026-0204, with the one remaining advisory pair (a Linux-only build-time proc-macro pinned upstream) suppressed with reason and expiry in `.cargo/audit.toml`. Agent-facing documentation: `docs/guides/agent-harness.md` (protocol, statistics semantics, the observe→act→measure→verify improvement loop, findings contract). Adversarial review (in-process multi-agent workflow with refuting verifiers + Codex CLI; thread `docs/threads/done/agent-harness/`) confirmed and led to four pre-release hardenings: a HIGH sandbox hole where `decoded-cache/` still resolved through decode.rs's private duplicate of repo-root discovery and escaped the harness sandbox (discovery is now deduplicated into `repo.rs`, closing a follow-up tracked since the 2026-06-10 split); stale async responses (screenshot/dump/stats) could be mis-delivered to the NEXT client connection after a timeout or Ctrl-C and mis-correlate with its reused request ids (completions now carry a connection generation and stale ones are dropped); `import_files` now rejects paths a real file dialog could never produce instead of persisting phantom library entries; and `click` now refuses controls whose `enabled` is false in the observe list (one shared predicate backs both), with the synthetic `tab_library`/`tab_detail` controls removed — the real UI has no tab buttons. Validation: 431 tests (69 new across protocol serde, statistics exactness, server framing/token/reconnect, command-execution parity with real user message sequences, wait-idle semantics including the save race, CLI parsing, storage-sandbox resolution and delegation, stale-response generation guards, click/import gating, and harnessctl), all four gates plus release build green, and a live end-to-end session: open → observe → screenshot → three slider edits → stats deltas in the predicted directions → before/after compare → save → export verified in the sandbox → quit with a finalized manifest, plus a post-fix smoke over four reconnections against a RAW fixture.

## 0.2.7 — 2026-06-13

Fix release: the Library no longer opens to dead placeholder tiles ("...") captioned with unfamiliar filenames. This turned out to be a test-isolation leak rather than a Library bug. The automated test suite resolved the per-user storage directory directly from `%LOCALAPPDATA%` with no override, so tests that import fixture files — and tests that create collections — overwrote the real `library.txt` (and `collections.json`) with temporary-directory paths (`first.dng`, `second.dng`, `overlay.svg`, and a phantom empty "Favorites" collection). When the OS later cleaned those temp directories, the saved entries pointed at files that no longer existed, and the grid drew them as empty placeholders with the fixture names as labels. What changed: in test builds the storage directory now resolves through an in-process, per-thread override that defaults to "no directory", so the suite can neither read nor write your real library or collections files; opt-in persistence tests point it at an isolated temp directory. Production builds are unchanged and still use `%LOCALAPPDATA%/photo`, and library and collection persistence now share that single storage-directory resolver so neither can leak again. The already-polluted `library.txt` was cleaned back to its one real entry. Validation: 362 tests (5 new: default isolation, the import path no longer touching real user data, and save/load round-trips through an isolated directory), all four gates plus release build green, multi-CLI review.

## 0.2.6 — 2026-06-12

Calibration + performance release. The RAW develop tone introduced in 0.2.5 was tuned against a single photo and read slightly over-bright on indoor scenes and over-contrasted on daylight ones; it is now calibrated across 35 real Sony ARWs (daylight and indoor) against each photo's embedded camera preview, landing on +0.85 EV with the same contrast — the new constants beat the old on both average match (36.0 vs 46.6) and worst-case match (56.3 vs 80.1), confirmed visually on the extremes. Cached developments re-derive automatically — the tone constants are now folded into the decode-cache contract itself, so any future retune invalidates stale looks structurally (review-caught: this release would otherwise have kept serving the old tone for every already-viewed RAW). Editing also got dramatically faster with identical output: the background bake that runs after every committed edit no longer computes an unused blur pass when Clarity and Dehaze are zero, per-pixel work skips adjustment stages that are at their defaults, and the full-resolution render now uses all CPU cores — a typical 24 MP commit render dropped from ~9 s to ~0.25 s and a Clarity/Dehaze render from ~9.8 s to ~2.1 s in like-for-like measurements (saves, background bakes, and library thumbnail refreshes all benefit). Validation: 354 tests including every pixel-exact persistence and parity regression unchanged, plus a manual perf probe and the multi-image calibration harness (now with a directory mode and aggregate scoring).

## 0.2.5 — 2026-06-12

RAW photos no longer develop duller and darker than the camera's own rendering. rawler's development performs demosaic, white balance, and color conversion but applies no tone curve, so the full-resolution image looked flat next to the embedded JPEG preview shown during loading (and next to Lightroom, which applies a baseline exposure and default contrast curve). Developed RAWs now receive a default tone — a +1.0 EV exposure lift plus a contrast S-curve (the app's own validated darktable-style power-law at strength 65) — tuned by percentile-matching the embedded camera preview of a real Sony ARW: tuned luma percentiles land within a few points of the camera rendering across the whole range (p5..p95 [8,32,55,92,168] vs the camera's [7,28,54,95,170]) with comparable clipping. Embedded previews and thumbnails are untouched (they already carry the camera's curve), so the staged-loading handoff from preview to full image no longer visibly dims. The decoded-image cache re-derives previously cached flat developments automatically. Editing is unaffected mechanically: sliders operate on top of the new base look, and previously baked edits keep rendering exactly as committed. The constants are single-reference-tuned in this release; per-camera tuning remains future work. Validation: 354 tests (5 new: tone identity/monotonicity/endpoint anchoring, develop-wiring equality, and an env-gated tuning harness), before/after/reference comparison renders reviewed visually with metrics recorded in the devlog.

## 0.2.4 — 2026-06-11

Fix release closing a pre-existing edit-corruption window found by the post-release verification review of 0.2.2. Editing a photo that already had baked edits, then browsing enough other photos for it to drop out of the in-session image cache, then returning to it, made the app reload the freshly written bake from disk while still holding the session's slider state — so the same edits rendered twice on screen and were immediately re-baked twice into the stored copy, compounding on every revisit. The app now tracks the generation id of each photo's latest completed bake: when a reload hands back exactly that bake, the session's already-absorbed slider state resets to defaults instead of re-applying (the image looks identical; undo history for that photo is dropped at that point, matching the existing undo-is-session-only contract). A reload that races a still-running bake adopts that bake's own pending base instead of the stale disk copy, so newer unsaved adjustments survive the race untouched. The review of this fix caught three further holes, all closed here: undoing edits back to defaults on an already-baked photo now correctly re-bakes the revert (the skip that avoided pointless identity re-bakes could previously swallow it, leaving the undone edit on disk and resurrectable); stale redo entries are cleared when a reload hands back a bake that already absorbed the session's edits (re-applying them would have doubled the edits); and adjustments committed in the brief window while a photo is reloading, which have no base to bake against, now reset with a visible status notice instead of silently corrupting or vanishing. Reopening a never-edited baked photo also no longer performs a wasteful full-resolution identity re-bake (nor logs a spurious warning per open while the source media is offline). Validation: 349 tests (11 new across the absorption, racing, revert, redo, notice, and owed-bake paths).

## 0.2.3 — 2026-06-11

Save-as-copy exports no longer write next to the original photo. Previously, saving produced `<name>_edited.<ext>` in the source folder — for photos opened from a camera card, that wrote onto the card itself. Exports now land in the gitignored `edited/` directory inside the photo repo (RAW sources still export as PNG), the directory is created on demand, and the status bar shows the full destination path after every save. Re-exporting the same photo overwrites its previous export, matching the old same-name behavior. When the app runs without a repo root (packaged exe outside the repo), the previous next-to-the-original behavior remains as the fallback. Validation: 338 tests (repo-rooted path expectations, no-repo-root fallback, export-directory creation; existing pixel-correctness save tests now run inside isolated repo overrides).

## 0.2.2 — 2026-06-11

Fix release: the Library now reflects committed edits even when the source media is offline (unplugged camera card, remapped drive letter). Previously, baked local edits were only readable while the original file was reachable with byte-identical metadata: cache lookups derived their key through `fs::canonicalize` (which fails for offline paths) and refused to load without reading live source metadata, so edited thumbnails reverted to originals or blank slots, and Detail could not open the edited image at all. Worse, library entries on offline media were silently evicted at startup, and the next library save made the eviction permanent. What changed: (1) baked local edits load through reachability-independent cache keys and are served as the authoritative pixels whenever the source file is absent — a present-but-rewritten source still invalidates the bake exactly as before; (2) library membership is now persistent: entries whose files are offline stay in the library and show their baked edited thumbnails (never-edited offline entries keep an empty slot until the media returns); (3) opening an edited photo in Detail works offline from the baked copy; (4) edits committed while a RAW photo was still developing its full-resolution image are no longer lost when you navigate to another photo before the develop finishes — the bake now completes from the finished decode in the background; (5) fixed a race where a library thumbnail could briefly show edits applied twice (the session edit state re-rendered on top of an already-baked thumbnail). Saved-edit files on disk are fully compatible in both directions. Validation: 332 tests (12 new regressions covering offline loading and key resolution, owed bakes across navigation, provenance-aware thumbnail rendering, and offline library persistence).

## 0.2.1 — 2026-06-10

Interaction fix: pressing Escape while the crop tool is active now cancels cropping and stays on the image in Detail view (previously it fell through to the back-to-library navigation, landing on the empty-library screen when the image was opened directly). A crop drag in progress at the moment of cancellation is discarded — releasing the mouse afterwards no longer commits the abandoned selection. Overlays still take priority (a visible context menu or rename field consumes Escape first); the navigation meanings (leave collection Detail, back to Library) apply on the press after the crop is cancelled. Validation: 319 tests, including new app-level and viewer-level regressions for both the navigation and the mid-drag cancellation paths.

## 0.2.0 — 2026-06-10

Breaking: editing sliders now follow Adobe Lightroom's UI conventions, and saved slider values from earlier versions mean different strengths on the new scales (baked local edits keep rendering identically — pixels, not operations, are persisted). What changed: Exposure runs −5..+5 EV (was ±3); Contrast, Saturation, Clarity, Dehaze, Temperature, and Tint all run −100..+100 (were ±50/±50/±50/±50/±60/±60); Saturation −100 now produces exact grayscale and +100 doubles chroma; Temperature ±100 spans the same 3200K–9800K tungsten-to-cloudy range as before at finer per-unit resolution. Strength envelopes validated by the April tuning audit are preserved at the new extremes (contrast power-law exponent 0.5–1.5, clarity/dehaze gain ±0.5). The four tone zones were retuned for targeted response: band Gaussians tightened to σ=1 (from √2) and per-slider reach set to 1.5 EV at the band center (combinations still clamp at ±2 EV total), so Highlights −100 reads as highlight recovery instead of a global exposure cut. Also fixed under review: neutral temperature/tint now produces an exact identity matrix, closing a pre-existing subtle preview-vs-export mismatch at default settings, and the slider readout shows Exposure at two decimals and the ±100 sliders as integers. Validation: 317 tests including new mapping, band-isolation, smoothness, extreme-value, and neutral-identity regressions; CPU/GPU parity is now structural (both paths share the same `edit::*_amount` mapping functions); rendered before/after grid reviewed visually; three-reviewer multi-CLI review converged at iteration 1.

## 0.1.6 — 2026-06-10

Test-reliability release; no behavior changes. Fixed a CI-only flake in the persisted decode cache's same-size-rewrite test: the cache's metadata fast path intentionally treats same-size, same-mtime files as unchanged, and fast runners could rewrite a file within one Windows file-time tick, making the change invisible. The test now guarantees an observable mtime change before asserting invalidation, with a new regression covering the helper (suite is now 299 tests).
