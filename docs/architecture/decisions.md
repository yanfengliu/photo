# Key architectural decisions

Append-only. A decision is never deleted; a newer one supersedes it and says so. Decisions made before the 2026-11-19 restart belong to the previous app and are in git history before commit `94bd2cf`.

| # | Date | Decision | Why | Alternatives rejected |
| --- | --- | --- | --- | --- |
| 1 | 2026-11-19 | Restart from an empty repository instead of evolving the iced viewer. | Its edit source was 8-bit sRGB even for RAW, its persistence was baked pixels with session-only undo, and its adjustment math existed twice (WGSL and Rust). Each is the opposite of a parametric raw developer, and most of the code served those contracts. | Incremental migration: would have meant replacing the pixel type in every layer, the persistence model and the renderer while keeping the app working, with little of the original surviving. |
| 2 | 2026-11-19 | Parametric settings are the source of truth; originals are never written; pixels are always derived. | It is what makes edits reversible forever, history and virtual copies cheap, and presets and copy/paste possible. | Baked pixel copies (the previous app's model). |
| 3 | 2026-11-19 | One CPU develop pipeline in linear Rec. 2020 `f32`, used for previews and export alike. | No parity surface between preview and export; testable without a GPU; deterministic. Fast enough at preview resolution on current multi-core machines. | GPU shaders with a CPU mirror (the previous app; chronic parity defects). GPU-only (tests need an adapter, export needs tiling and read-back, behaviour varies by backend). If speed is needed later: a 3D LUT baked from the same Rust functions. |
| 4 | 2026-11-19 | Sources are linear `u16` (65535 = 1.0); RAW stays camera-native and un-white-balanced until render time. | Half the memory of `f32` at 60 MP with more precision than a sensor delivers; white balance and highlight recovery need the unbalanced, unclipped data. | 8-bit display-referred sources (no recovery latitude). `f32` sources (722 MB for a 60 MP file before any working buffer). |
| 5 | 2026-11-19 | egui/eframe for the UI. | Dense tool panels and custom-painted editors are cheap in immediate mode; virtualized scrolling is built in; cargo-only and cross-platform; `egui_kittest` gives headless interaction and real frames inside `cargo test`. | iced (custom widgets and virtualization cost much more; the previous app needed a bespoke harness). Tauri with a web front end (a second toolchain outside the gates, and frames have to cross a process boundary). Native toolkits (not cross-platform). |
| 6 | 2026-11-19 | The catalog is a single SQLite file with develop settings stored as JSON. | Transactions, indexes and queries for free; JSON keeps settings forward- and backward-compatible through serde defaults. | Text and JSON files (the previous app; no queries, no transactions). A column per adjustment (every new slider becomes a migration). |
| 7 | 2026-11-19 | Each responsibility is a crate and the dependency graph is the architecture. | Boundaries are enforced by the compiler rather than by review; crates compile in parallel and can be built independently. | One crate with modules (boundaries become conventions). |
| 8 | 2026-11-19 | Only the entry point resolves a default storage location; every library function takes explicit paths. | The previous app's test suite once overwrote the real library. This makes that impossible by construction rather than by a test-only override. | A `cfg(test)` override on a global resolver (works, but depends on every test opting in correctly). |
| 9 | 2026-11-19 | Slider names, ranges and `crs:` XMP values follow the conventions photographers know; the rendering math is our own and cites its real sources. | Familiar controls and interoperable sidecars without claiming a parity that cannot be verified. | Chasing pixel parity with a proprietary renderer (unfalsifiable; the previous app's local rules already forbade the claim). |
| 10 | 2026-11-19 | Tone controls act in perceptual space (gamma 2.2, pivot 0.5), each as its own monotonic curve, composed rather than summed; highlights and shadows are applied as a gain looked up from an edge-aware base. | Monotonic by construction, which the previous app's summed Gaussian bands were not; local contrast survives the full slider range. | Summed per-band EV offsets (non-monotonic at extremes, posterized). Purely global curves (flatten local contrast when pushed). |
| 11 | 2026-11-25 | An export never replaces a file it has not identified. A name is taken only by a move that cannot replace (a hard link, an exclusive rename, or an exclusive create and copy), and under the overwrite policy the existing file is moved aside and recognised by file identity before anything is removed. | Check-then-rename leaves a window in which an original moved onto the destination is destroyed (review F29, F30). Identity is read at the moment of comparison because FAT and exFAT under macOS change a file's identity when it gets its first bytes. | Comparing paths (misses hard links, letter case and moved files). A reservation file that is then renamed onto (a file another program renames onto it is replaced, and an empty file shows under the final name). |
| 12 | 2026-11-25 | Nothing is synced to disk before an export takes its name. | An export can always be made again from the catalog, and a full flush per file on macOS costs more than the export itself in a batch. The module doc says what power loss can leave. | Syncing before the move (durable, and slow). |
| 13 | 2026-11-25 | An edit that is still open is committed before any command that reaches that photo (a virtual copy, a removal, undo or redo of a step on it, metadata read over it, export, closing), and only then. | Nothing in the app has a save step, so no path may drop what the user is looking at; a command on other photos must not end a drag in progress. | Committing before every command (ends an unrelated drag; review F37). Dropping open edits on such commands (silent loss). |
| 14 | 2026-11-25 | A quarter turn or a mirror of a developed photo has one implementation, `DevelopSettings::turn` in `photo-core`, which carries the crop rectangle, a fixed ratio and the straighten angle. The perspective transform is left as it is. | The Library's rotate changed the orientation alone and left the crop on other content, while the crop tool had its own correct copy; two copies of geometry drift apart. | Turning in the engine and in the interface separately. Turning the perspective sliders as well (their axes are named for the frame as it is seen, and mapping them needs a pipeline-level proof this change did not have). |
